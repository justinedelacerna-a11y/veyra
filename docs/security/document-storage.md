## 2. Bucket Design

### `vehicles-marketing` (Public)
- Contains: vehicle catalog photos, exterior shots, feature images
- Read: public (no authentication required)
- Write: service_role only (staff upload via admin panel)
- CDN cache: enabled
- File types allowed: JPEG, WebP, PNG
- Max file size: 8 MB per image

### `customer-documents` (Private — Highly Sensitive)
- Contains: driver licenses, government IDs, address proofs, passport scans
- Read: **no direct public access under any circumstances**
- Write: customer uploads via server-validated Server Action
- Access model: short-lived signed URLs issued by Next.js server only
- Encryption: encrypted at rest (Supabase default)
- File types allowed: JPEG, PNG, PDF
- Max file size: 10 MB per document

### `inspection-photos` (Private — Internal)
- Contains: pre-trip and post-trip inspection photographs, damage photos
- Read: **no direct public access**
- Write: staff via server-validated Server Action
- Access model: signed URLs, scoped to the reservation
- File types allowed: JPEG, PNG, WebP
- Max file size: 20 MB per photo (high-res damage documentation)

### `invoices` (Private — Sensitive)
- Contains: PDF invoices, receipts
- Read: customer (own invoices) or finance/admin
- Write: server-generated only (never direct customer upload)
- Access model: signed URLs
- File types: PDF only

## 3. Upload Flow (Private Documents)

All customer document uploads must go through the server, not directly to Supabase Storage from the browser.

```
1. Customer selects file in browser
2. Browser sends file to: POST /api/documents/upload (Next.js Server Action)
3. Server:
   a. Authenticates Clerk session
   b. Validates file: MIME type, file size, file extension
   c. Scans file: (future) virus/malware scan integration
   d. Generates unique storage path:
      customer-documents/{customer_id}/{document_type}/{timestamp}-{uuid}.{ext}
   e. Uploads to Supabase Storage via service_role
   f. Creates customer_documents record in PostgreSQL
   g. Returns success/failure (NOT the storage path)
4. Browser displays upload confirmation
```

**The browser never receives the raw storage path.** It only receives the document ID from the `customer_documents` table.

## 4. Access Model — Signed URLs

Private documents are accessed exclusively via signed URLs generated by the server.

```typescript
// Pseudocode for signed URL generation
async function getDocumentSignedUrl(
  actorId: string,
  documentId: string
): Promise<string> {
  // 1. Fetch document record
  const doc = await db.customerDocuments.findById(documentId)
  if (!doc) throw new NotFoundError()

  // 2. Authorize: does this actor have permission to view this document?
  const customer = await db.customers.findByUserId(actorId)
  if (doc.customer_id !== customer?.id) {
    // Also allow: support, admin, superadmin
    const staff = await db.staffUsers.findByUserId(actorId)
    if (!staff || !['support','admin','superadmin'].includes(staff.role)) {
      throw new ForbiddenError()
    }
  }

  // 3. Generate signed URL via service_role (server-side only)
  const { data, error } = await supabaseAdmin.storage
    .from('customer-documents')
    .createSignedUrl(doc.storage_path, 900) // 15 minutes

  if (error) throw error
  return data.signedUrl
}
```

**Signed URL TTL: 15 minutes maximum.** URLs are not cached. Each request generates a fresh URL.

## 5. File Validation Rules

All uploads must be validated server-side before storage:

| Check | Rule |
|---|---|
| MIME type | Must match allowed list for the bucket; verify actual content (not just extension) |
| File extension | Must match allowed list and must match MIME type |
| File size | Must be within bucket-specific limit |
| File content | Future: virus scan via ClamAV or equivalent SaaS |
| Filename | Sanitized and replaced with server-generated name — never trust client filename |
| Path | Storage path is server-generated — client never specifies the path |

## 7. Auditability

Every document access (signed URL issuance) must create an audit event:

```
actor_id: staff_id or customer_id
action: document.signed_url_issued
resource_type: customer_document
resource_id: document_id
details: "Signed URL issued for {document_type}; expires in 15 minutes"
```

Every document upload, approval, rejection, or deletion must also create an audit event.

---

## 8. Prohibited Practices

- ❌ Never expose private bucket paths or URLs in API responses
- ❌ Never store document storage paths in localStorage or sessionStorage
- ❌ Never generate signed URLs with TTL > 15 minutes for identity documents
- ❌ Never allow direct client uploads to private buckets (bypass server validation)
- ❌ Never include signed URLs in email bodies (email is not an access-controlled channel)
- ❌ Never log raw signed URLs in application logs

---

## 9. Staff Document Access (Operational)

Staff reviewing customer documents in the admin panel:

```
1. Staff navigates to Customer → Documents
2. Server: authenticates staff (branch_staff or above)
3. Server: checks permission: support/admin/superadmin can view docs
4. Server: fetches customer_documents record (metadata only)
5. Staff: clicks "View Document"
6. Server: generates 15-minute signed URL
7. Browser: opens signed URL in new tab or inline viewer
8. URL expires after 15 minutes
9. Audit event created for the access
```
